# Webで1本の動画と工程の順序を確認する

トップ画面の「動画で工程と順序を確認」で、工程名・何が見えれば確認できるか・期待する順番を編集し、
動画を1本アップロードできます。工程の追加・削除・上下移動に対応しています。

「この動画で工程を確認」は、設定したOpenAIまたはローカルQwenへ実際の動画サンプルを渡す処理です。
`mock`は動画の判定を作りません。モデルが未接続のときは実行ボタンを無効にします。
モデルの認識結果は候補として扱い、工程ごとの引用画像・理由・不確実性から確認します。

結果では、4区間のレビュー画像、元動画、工程ごとの根拠画像を表示します。
工程や時刻を選ぶと元動画へ移動できます。根拠がない未確認の工程には、別の工程の画像を流用しません。
基準・順序・動画・画像間隔・追加確認の選択を変更すると以前の判定を消し、条件が違う結果を混ぜません。

## 判定と順序

動画の工程判定は`observed`（観測あり）と`unknown`（未確認）の2つです。
画面外や画像が足りない工程を「未実施」とは判定しません。信頼度やヒートマップは生成しません。

隣り合う工程の引用画像を比較し、前工程の最大時刻が次工程の最小時刻より早ければ`sampled_before`、
引用時刻が完全に逆なら`violated`、重なりや未確認があれば`unknown`です。
順序の計算はMCP・ローカル検証スクリプトと共有しています。
これはサンプル画像の順序であり、連続した実行や動作の開始・終了を測ったものではありません。

## 未確認を自動で追加確認する

画面では「未確認の工程を追加画像で再確認する」が初期状態で有効です。
初回で未確認があれば、MCPの[自動ワークフロー](automatic-reference-workflow.md)と共有する処理で
前後の観測時刻から検索範囲を決めます。必須の文脈画像を残し、レビュー済み時刻の大きな空白から
中間画像を追加します。希望する最大空白か画像予算に達すると計画を終了します。
文脈画像を削って予算に合わせることはありません。画像計画中はモデルを呼びません。

追加確認は最大1回、未確認の工程IDだけを再判定します。前に観測した工程の理由・引用時刻・不確実性は保持し、
統合した引用から順序を再計算します。元動画のハッシュを段階間で確かめ、同じ動画から実画像を抽出します。
検索範囲は手掛かりであり、範囲外の実施や順序違反を否定する根拠ではありません。

初回と最終の切り替えで、4区間の画像もその段階のサンプルに切り替わります。
工程ごとの初回→最終の状態、入力画像数・新しい時刻の数、最大レビュー時刻の空白と終了理由を確認できます。
空白の値は検索範囲内の時刻間隔です。短い動作や範囲外の動作を必ず拾えるという意味ではありません。

| 終了理由 | 内容 |
|---|---|
| `no_unknown_steps` | 初回または追加確認後に未確認なし。順序違反は別に表示 |
| `unknown_after_followup` | 追加確認後も未確認が残るため終了 |
| `no_new_samples` | 予算内の計画で新しい画像がなく、初回を保持 |
| `refinement_budget_exhausted` | 計画を画像予算に収められず、初回を保持 |

モデル呼び出し・デコード・回答検証が失敗した場合はリクエストをエラーにし、初回を最終成功として表示しません。
追加確認を無効にすると、従来と同じ初回1回の判断になります。

## キーなしで前回の実MCP結果を見る

「記録済みの工程確認を見る」は、32秒の映像に対する前回の実Codex MCP判断を再生します。
新しい推論や、アップロードした動画への判定には使いません。

- 初回と最終結果を切り替え、引用画像の違いを確認できます。
- 4工程は観測あり、乾燥は追加確認後も未確認、全体の順序も未確認です。
- 2回の画像判断と、0.25秒間隔が予算超過して0.5秒になった記録を表示します。
- 元動画・初回結果のハッシュ、両段階の引用と順序、既に観測した判断の維持を検証してから画像を読み込みます。

## API

`POST /api/video-flow/verify`はmultipartで次を受け取ります。

| フィールド | 内容 |
|---|---|
| `video` | 元動画1本。既存の容量・時間制限を適用 |
| `reference_json` | `title`と`steps`。工程は一意な`id`、`label`、任意の`criterion`。1〜30工程、JSONは最大65,536文字 |
| `sample_interval_seconds` | 希望する間隔。初期値0.75秒、0.25〜30秒 |
| `auto_refine` | 自動追加確認。APIの初期値は`false`、Web画面では初期状態で選択済み |
| `refinement_interval_seconds` | 検索範囲内のレビュー時刻の希望最大空白。初期値0.25秒、0.25〜30秒。予算に達すると未達でも終了 |
| `refinement_max_frames` | 文脈画像を含む追加入力の予算。初期値24枚、2〜96枚。設定・プロバイダー上限でも制限 |

画像上限に合わせて間隔を広げ、末尾までサンプリングします。ローカルQwenでは最大24枚です。
動画は両段階で同じ一時ファイルを使い、リクエスト終了時に削除します。モデルにはサンプル画像と基準を渡します。
モデルが返した工程IDや引用時刻を検証し、工程の欠落・重複・未提供の引用を502エラーで拒否します。
不正な基準は422、容量・時間超過は413、接続未設定は503です。

自動確認では`initial`に初回の判断とサンプル時刻、`workflow`に呼び出し数・予算調整・終了理由を返します。
追加実行時の`refinement`は検索範囲と追加／入力時刻を含みます。
`sampling_strategy=gap_bisection`、`coverage`に選択前後の最大空白・希望値・予算による未達を返します。
非等間隔の追加選択なので`workflow.interval_selection.chosen_interval_seconds`は`null`です。
旧記録の再生は従来の間隔調整履歴を表示します。
トップの画像と`sampled_seconds`は両段階の和集合なので、一定間隔を示す`sample_interval_seconds`は`null`になります。
引用時刻は追加回答が実際に見た入力だけを検証し、初回の別画像への引用も拒否します。

リポジトリのルートから、モデルを設定したバックエンドへ送る例:

```powershell
curl.exe http://localhost:8000/api/video-flow/verify --form "video=@docs/assets/video-demo/new-video-transfer/source.webm" --form "reference_json=<examples/new-video-handwashing-flow.json" --form "sample_interval_seconds=2" --form "auto_refine=true"
```

`GET /api/video-flow/status`の`reference_ready`と`reference_reason`で接続状態を確認できます。
`GET /api/video-flow/reference-demo`は記録済みの工程判定、
`GET /api/video-flow/reference-demo/video`はその元動画を返します。

OpenAI接続は既存SDKの`responses.parse`とPydanticの出力モデルを使用します。
拒否や出力不足を成功結果へ変えず、工程・時刻の整合性はアプリでも検証します。
[公式の構造化出力ガイド](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)に照合しました。
Qwenは実画像をGPUへ渡し、厳密な整数フレームIDを元動画のサンプル時刻へ変換します。
